## 0. Workspace rules (shared by every ZCommerce repo)

This repo is one part of the ZCommerce platform. The full map is in the workspace root `../CLAUDE.md` (`../../CLAUDE.md` for storefronts), when that file is present. The rules below are mandatory here even when it isn't.

1. **PRD first (tiered).**
   - **T1** covers: a new feature, page or module; a GraphQL contract change; a model or event change; auth, tenant, permission or billing logic; a new integration. T1 needs a PRD in `docs/prd/` with **Status: Approved** before any code. If none exists, draft one from `docs/prd/_TEMPLATE.md` (Status *Draft*) and **stop for approval**.
   - **T2** covers bug fixes, tweaks and small refactors. T2 needs only a line in `docs/changelog/YYYY-MM.md`.
   - Unsure of the tier? Treat it as T1 and ask.
   - Cross-repo PRDs have their source of truth in `zcom-backend/docs/prd/`; consumer repos keep a pointer PRD.
2. **Read docs before, update docs after (MANDATORY, no exceptions).** Documentation is part of the definition of done. Every change, including code, config, infra, dependencies and decisions, updates all related docs in the same change. Record decisions and approvals from conversation in the PRD or ADR immediately, before implementing. A task isn't finished while any doc disagrees with the code.
   - **Before** a change, read this file, `README.md`, `docs/README.md`, and the relevant PRD, ADR and architecture docs.
   - **After** it, in the same change, update whatever is now stale: the README (setup, commands, env names), `docs/architecture/*` (contracts), PRD status and implementation log, the changelog, `docs/README.md` (the index), and this `CLAUDE.md` (rules and known issues).
   - End every task with a **"Docs impact"** line.
3. **Ask, don't guess.**
   - Ask one precise question, with options and a recommendation, when the request conflicts with a PRD, an ADR, this file, or the code.
   - Do the same when docs and code disagree, or when a change would affect a contract, a security or tenant boundary, the design system, dependencies or deployment.
   - Don't ask about things you can verify in the code yourself.
4. **Scoped and safe.**
   - No drive-by refactors or mass reformatting.
   - Don't add dependencies without asking.
   - Never commit, push, deploy or touch databases unless asked.
   - Never print or commit secrets or `.env` values, including the token embedded in `git remote -v`.
   - Report checks honestly, keeping pre-existing failures separate from new ones.
5. **Coding style: the owner's signature (mandatory).** Follow the workspace `CODING_STYLE.md` (`../CODING_STYLE.md`, or `../../CODING_STYLE.md` for storefronts). Its baseline is the `zcom-backend` style.
   - 2 spaces, double quotes, semicolons, trailing commas, 80 columns.
   - Named exports with barrel `index.ts` files (React page and component files are the exception: `export default X;` at the end).
   - File names are `kebab-case.role.ts`.
   - Static-class controllers and services, with `return await`.
   - `xEnum = {…} as const`; the `I` prefix only for Mongoose documents; `UPPER_SNAKE` constants with unit suffixes (`_MS`, `_DAYS`).
   - `GraphQLError` with `extensions.code`; one `createLogger({ service })` per module.
   - JSDoc module headers and `// ─── ` section dividers.

   **New files** follow it exactly. **Edits** keep the file's existing formatting; never reformat untouched code. When you commit, use Conventional Commits: `type(scope): summary (PRD-NNN)`.
6. **Storefront specifics.**
   - Use only backend operations listed in the storefront contract doc, and validate field-level.
   - The server computes money.
   - **Plumbing lives in `@zcom/storefront-kit`** (PRD-002, the kit's `docs/prd/PRD-002-storefronts-onto-the-kit.md`): the proxy, the Apollo Client 4 link chain, the customer session, guest cart id, consent and tags, attribution, payment launcher and return, `/checkout/start`, stock and sort helpers, security headers. ## 1. What this is

The **Rare Element** brand storefront (the brand name in content and assets is **Nahara**, `assets.nahara.co.in`, site `nahara.co.in`). It's a custom-designed shopper site on ZCommerce, with home, product listing and detail, category catch-all, account (orders, settings, wishlist; the fake offers page was removed by PRD-014 UX-06), checkout (the store's payment app: Nimbbl, Razorpay, Cashfree or PayU, PRD-011) and login. It is the **reference pattern for new storefronts**.

**Stack (PRD-002 D3, one version table with the kit and Deveshe Dreams, 2026-11-10):**
- Next.js 16.4 with the **App Router** (`src/proxy.js`, Turbopack), React 19.3, **JavaScript**.
- **`@zcom/storefront-kit` 1.x** (installed from its GitHub tag; builds need the shared `GITHUB_TOKEN`, `vercel.json`; its build-on-install is approved in `package.json` `allowScripts`, pinned to the tag's commit, so a new tag needs `npm approve-scripts @zcom/storefront-kit`), Apollo Client 4.3 (a kit peer: the store's own queries share the kit's client) + `@apollo/client-integration-nextjs` (the kit's `ZcomSsrProvider`), graphql 17, rxjs 7, zustand 5, react-hook-form + zod 4.
- GSAP 3.15 (public package) with ScrollTrigger and CustomEase, `lenis`, Swiper 14.
- three / R3F (dynamic import, `ssr: false`), lottie-react (only through `LazyLottie`, JSON fetched from `/public`), `@remixicon/react` icons, react-toastify, `html-react-parser` (also used by the sanitiser).

**Removed:** `nimbbl_sonic` (Nimbbl retired, PRD-002 kit), `uuid` (PRD-002 round 3; guest ids are server-issued since R2-C2), `js-cookie` and `cross-fetch` (RMAINT-9), framer-motion earlier (SF-21).

**Integration status: on the current backend contract (PRD-002 WS-F1, round 2 R2-W6 and round 3, 2026-10-14).**
- All 61 operations validate against the composed backend schema (PRD-034 added `StorefrontTrackingConfig` and the `consent` argument on `CreateCheckoutSessionFromCart`, 2026-11-05; PRD-032 added the 13 review operations, 2026-11-04, incl. `GetProductReviewSummary`; PRD-020 FR-12 added `GetVariantAvailability`; PRD-015 FR-20 added `CancelMyOrder`, `CreateReturnRequest` and `CancelMyReturnRequest`; PRD-002 round 2 added `issueGuestCartId` and `mergeGuestCart`; round 3 added `unsubscribeNewsletter`; PRD-003 FR-0.5 added `customerRequestPasswordReset` and `customerResetPassword` for `/forgot-password` and `/reset-password`; PRD-014 FR-2.8 added `SubscribeNewsletter`, `GetProductReviews` and `GetSitemapProducts`, and FE-22 `GetClientSideProductsByIds`, which validates only once the backend supergraph is rebuilt with W2-BACKEND-REG's field). The contract is `../../zcom-backend/docs/architecture/storefront-api-contract.md`.
- **Tenant by host, through the kit's proxy (PRD-002 R2-C1, kit PRD-002 FR-4.1):** the browser calls same-origin `/v1/graphql`; `src/proxy.js` is the kit's `createZcomMiddleware`, which forwards it to `${API_GATEWAY_URL}/v1/graphql` with the edge headers (client tenant headers stripped, `x-tenant-domain`, `x-zcom-edge-secret`, only the customer refresh cookie forwarded, the shopper IP only from a trusted source: Vercel's header here), answers `/.well-known/zcom-store`, serves the branded 503 for a suspended store and guards `/account/*` and `/checkout/*` (except the result pages and `/checkout/start`). `EDGE_SHARED_SECRET` is required in production and staging (the kit refuses to call the gateway without it). Server components read through `lib/server-query.js` (the kit's `zcomFetch` with Nahara's own documents, revalidate 300 s); client components through the kit's `ZcomSsrProvider` (SSR pass on the gateway with the edge headers). A production build fails without `API_GATEWAY_URL` and `NEXT_PUBLIC_TENANT_DOMAIN`.
- **Newsletter unsubscribe (PRD-002 VCON-1):** `/unsubscribe` (`app/unsubscribe/page.jsx`, `noindex,nofollow`, + `unsubscribe-client.jsx`) is the target of the link the backend puts in campaign emails (`https://<tenant domain>/unsubscribe?email=…&token=…`, signed with `NEWSLETTER_TOKEN_SECRET`). It reads `email` and `token` once, removes them from the address bar (`history.replaceState`), and calls `unsubscribeNewsletter(email, token)`. The server answers uniformly, so every server answer shows the same neutral message; only a network failure offers a retry. The backend builds the link from the tenant's **configured domain**, so that domain must serve this storefront or redirect keeping the query string (FIN-3; the owner checks it per tenant).
- **Checkout requires login** (the backend checkout operations are customer-only). The guest cart id is server-issued (`issueGuestCartId`, R2-C2) and the guest bag is moved at login with one `mergeGuestCart` call (R2-C3).
- **Stock signal (PRD-020 FR-12, 2026-10-26):** `Variant.availability` / `availableQuantity` and `Product.availability` drive the PDP (struck-through sold-out options, "Sold out" + "Notify me", "Only N left" / "Low stock"), listing ribbons and the cart drawer (sold-out lines hold checkout); the PDP and the drawer re-read with `getVariantAvailability` (`hooks/useVariantAvailability.jsx`). **`null` renders exactly as before** (signal off by default per store, untracked, not seeded): then "Unavailable / Notify me" appears only when an option combination has no published variant or the backend answers `PRODUCT_UNAVAILABLE`. "Notify me" works for guests with an email; since CP-22 a guest's alert starts only after the emailed link to `/back-in-stock/confirm` is opened (`utils/back-in-stock.js`, twin of deveshe `utils/back-in-stock.util.js`), so a guest sees "check your email to confirm" and signed-in shoppers keep the old copy; `RATE_LIMITED` shows neutral copy. Checkout reservation stays the authority.
- **Order page (PRD-015 FR-20, 2026-10-26):** `/account/order/[id]` shows `displayStatus`, tracking (`shipment`), Cancel when `canCancel` and returns (`returnableItems`, `returnRequests`).
- **Reviews (PRD-032, 2026-11-04, not browser-tested):** the PDP review section (`components/product/ProductReviews.jsx`: the `Product.reviewSummary` summary from its own read `GetProductReviewSummary`, never part of the catalog query, failure = no summary; filters, sort, Load more, photos, store reply, Report) and "Write a review" (`components/product/reviews/`, `submitReview`, photos through `hooks/useReviewPhotoUpload.jsx`: media `requestReviewPhotoUpload` → a direct POST to S3, the presigned-upload exception → `confirmReviewPhoto` receipt); `/review?token=` (`submitReviewsWithLink`, no login) and `/review/unsubscribe` (both noindex, robots-disallowed); Account › Reviews; Product JSON-LD rating only with approved reviews (`utils/reviews.js` `buildReviewJsonLd`). Review photos use a plain `<img>` (their host isn't in `remotePatterns`); the CSP allows `https://*.amazonaws.com` in `connect-src` and `img-src` for them, and the media bucket needs a CORS rule for POST from this origin (owner). Pointer: `docs/prd/PRD-032-customer-reviews.md`.
- **Backend gaps shown as such:** no badge name (merchant ribbons); no password change while logged in (ChangePassword removed; a forgotten password is reset through `/forgot-password`, PRD-003 FR-0.5); cart and order lines link to `/products/<id>`, which redirects to the slug (the wishlist loads its products in one `getClientSideProductsByIds` call per 50 since PRD-014 FE-22); lookbook documents removed.
- Nothing has been tested in a browser or end to end against a running backend or any payment sandbox yet.

## 3. Rules

- **App Router conventions.**
  - A server `page.jsx` fetches data with the RSC client and exports `metadata` or `generateMetadata` (with a per-route canonical). Interactivity goes into a sibling `*-client.jsx` with `'use client'`. Add a `loading.jsx` for new routes.
  - Never import `next/router` (use `next/navigation`). Don't use Pages Router APIs.
  - Call `notFound()` only for a null result or `NOT_FOUND`; other errors go to `app/error.jsx`.
- **Caching.** Catalog pages use `export const revalidate = 300`. Keep account, cart and checkout dynamic, and never cache per-user data.
- **Data.**
  - Server components use `serverQuery` from `lib/server-query.js` (the kit's `zcomFetch`: it throws on any error except `NOT_FOUND`, so `notFound()` stays for real misses); client components use Apollo hooks (`@apollo/client/react`) under the kit's provider. `context.skipAuth` sends a request anonymously.
  - **`EDGE_SHARED_SECRET` is server-only.** Only the kit reads it (proxy, `zcomFetch`, the SSR pass of `ZcomSsrProvider`). Never prefix it with `NEXT_PUBLIC_`, and check `.next/static` for it after build changes.
  - Cart operations go through `useVisitor().runWithGuestId` (never invent a guest id client-side).
  - gql documents go in `graphql/`. No inline `gql`.
  - Show errors with `utils/errors.js` (branches on `extensions.reason` / `code`).
  - Site URL and support email come from `utils/env.js` (env with the current Nahara defaults). **Tag ids come from the backend (PRD-034 FR-1.2):** the kit's `ZcomTags` (`providers.jsx`) reads `storefrontTrackingConfig` and takes the backend GA4 / Pixel / Google Ads ids, else the env fallback it is given (`NEXT_PUBLIC_GA_MEASUREMENT_ID`, `NEXT_PUBLIC_FB_PIXEL_ID`; GTM is env only); malformed ids load nothing.
- **Auth and tokens.**
  - The session is the kit's (`tokenManager`): the access token lives **in memory only** and refreshes 60 s before expiry with `customerRefreshToken` (single-flight); the refresh token is the HttpOnly `__Host-zc_cust_rt` cookie; never select or store `refreshToken`. An auth answer (UNAUTHENTICATED, FORBIDDEN, INVALID_AUTH_TOKEN, TENANT_MISMATCH) ends the session and Nahara toasts "Your session has ended"; network, 429 and 5xx errors never do. `TENANT_NOT_FOUND` shows one "store unavailable" toast (`onStoreUnavailable`).
  - The legacy `refresh_token` cookie isn't forwarded by the kit's proxy (kit PRD-002 D10). A shopper's pre-kit sign-in hint, guest bag id, consent and click ids are moved to the kit's keys once on the first visit (`migrateLegacyStorage`).
  - Login and signup honour `?next=` only through `utils/redirect.js` (same-origin check with `new URL`, RSEC-6); without a valid `next` they go to `/`. The Apollo store is reset at login and cleared at logout.
  - The persisted auth store holds no PII (RSEC-11: `partialize` + v1 migration); the profile is reloaded from `getMyProfile` after a reload.
- **Money and checkout.** The server computes every price and total. Checkout (`app/checkout/[id]/checkout-client.jsx`): `createCheckoutSessionFromCart` (inline address, plus the kit's `buildAttribution()` (GA ids and UTMs with analytics consent, ad click ids with ads consent) and `buildCheckoutConsent()`) → poll `getCheckoutSession` (1 s, up to 30 s) until RESERVED → `completeCheckout` → `createPaymentSession({orderId})` → `openPaymentCheckout` (`utils/payment-checkout.js`: the kit's `launchPayment`, only to known payment hosts, 20 s script timeout; Razorpay / Cashfree windows, PayU form post; Nimbbl is retired) → `verifyPayment` (provider response + `paymentId`) → thank-you; PayU and Cashfree redirects return through `app/api/payments/return/route.js` (303) to `/checkout/payment-return`, which verifies with the shopper's session → which polls `myOrder` (3 s, up to 60 s). The Pixel and Google Ads purchase fire only when PAID, once per order (the GA4 purchase is sent by the backend, PRD-012). The unpaid order id is kept in `sessionStorage` per cart with a fingerprint of the lines and coupon and, since VBUG-4, of the checkout details (email + shipping + billing address as sent) (`utils/pending-order.js`, RBUG-8); while it exists the bag is locked and a retry (also after a reload) pays that order, but only while both fingerprints match: a changed address or email creates a new order, and a legacy entry without the details fingerprint is never reused. `CHECKOUT_REPLACED`, `PAYMENT_NOT_CONFIGURED`, `MISSING_PROVIDER_ORDER` and `INVALID_EMAIL` have messages in `utils/errors.js` (VCON-2). The backend also reuses the active checkout session for an unchanged cart (R2-C8). The thank-you page ends on a "Payment not confirmed yet" state when polling ends without PAID (RBUG-20). **PRD-014 Wave 1:** a ₹0 total is placed PAID by `completeCheckout` (COM-08; `COMPLETE_CHECKOUT` selects `pricing { total }`), so the client skips `createPaymentSession` and the provider and goes straight to thank-you; `SHIPPING_UNAVAILABLE` (no shipping zone covers the address) shows "We can't ship to this address yet" and focuses the address (state) field, which stays editable; a cart remove always sends the line's `variantId`, and a `VARIANT_REQUIRED` answer (COM-32) shows `REMOVE_ITEM_OVERRIDES` copy and refetches the bag.
- **HTML and JSON-LD.** Render CMS HTML only through `utils/sanitize-html.js`, and JSON-LD only through `utils/json-ld.js` (the kit's `serializeJsonLd`).
- **Styling.**
  - Use plain CSS imported via `styles/allCssImport.css`, plus the existing utility classes in `globals.css`. Match the page you're in.
  - Don't add Tailwind, CSS-in-JS, or a UI kit.
  - Fonts: `next/font` Inter plus `styles/fontSetting.css`.
  - Icons: `@remixicon/react`.
- **Animation.**
  - GSAP plugins are registered once in `providers.jsx`. Use `useGSAP` or `gsap.context` + `revert()` for cleanup; **never** `ScrollTrigger.killAll()` (SF-20).
  - Lenis is the single `LenisScroll` (`window.lenis`).
  - Lazy-load three/R3F (`dynamic`, `ssr: false`) and lottie (`LazyLottie`), and respect `prefers-reduced-motion` in new animations.
- **Accessibility (PRD-014 UX-31).** Icon-only controls are `<button>`s with an `aria-label` (decorative icon `alt=""`). Drawers and the mobile menu are `role="dialog"` + `aria-modal` + `tabIndex={-1}` and use `hooks/useDialogA11y.jsx` (focus in, Tab trapped, Escape closes, focus back to the opener, `inert` while closed). The hero shows its final state for `prefers-reduced-motion` (UX-30).
- **Images.** Use `next/image` with `sizes` on responsive and `fill` images. `remotePatterns` allows only `assets.nahara.co.in`; adding hosts needs approval (and a CSP update).
- **Headers.** `next.config.mjs` builds every security header with the kit's `buildSecurityHeaders` (payment apps, GA4/GTM, Meta and Google Ads, the platform media CDN and S3 upload hosts, `frame-ancestors 'none'`, HSTS in production) plus Nahara's `assets.nahara.co.in`; `CSP_REPORT_ONLY=true` switches the CSP to report-only for rollout. `script-src` keeps `'unsafe-inline'` on purpose (SF-9 partial): a per-request nonce forces dynamic rendering, which ends ISR on catalog pages, and GTM custom-HTML tags need it.
- **Consent first (PRD-014 FR-1.9, D10).** `layout.jsx` runs only the kit's Consent Mode v2 defaults (`CONSENT_DEFAULT_SCRIPT`: every type denied, then the stored choice). `components/common/ConsentBanner.jsx` asks once (Accept all / Reject all / Manage: analytics, marketing) and saves through the kit's `updateConsent` ("marketing" is the kit's "ads"); the kit's `ZcomTags` then loads GTM + GA4 with analytics consent and the Meta Pixel + Google Ads tag with ads consent, revokes the Pixel's consent on withdrawal, and pushes `zcom_consent_update` to the dataLayer (`zcomConsentAnalytics`, `zcomConsentAds`: **a non-Google tag in a merchant's GTM container must fire on a trigger that requires `zcomConsentAds`**, W1V-C-05). The footer "Cookie preferences" reopens the banner (the kit's `openConsentPreferences`). Never add a tag script by hand. **Ads (PRD-034 FR-1.3, D8):** e-commerce events go only through `trackEcomEvent` (`utils/analytics.js`), which calls the kit's ads functions; item ids are **variant ids**; the purchase uses the order `_id` as Pixel `eventID` and Google `transaction_id`; enhanced conversions hash the email and phone in the browser. Checkout sends the click ids and `_fbp` / `_fbc` only with ads consent and always the consent snapshot. Attribution (UTMs, GA ids) is stored and sent only with analytics consent, landing page as a path only.
- **Analytics.** The kit sends the Pixel `PageView` on client-side navigations. Use `utils/analytics.js` for e-commerce events; GA4 events go only with analytics consent and are queued until GA4 loads (the kit's `trackEvent`, to GA4 only). `view_item`/`ViewContent` fire once per product view, not on option changes (FE-24).
  - **Event layer (PRD-013 FR-4).** `utils/analytics-events.js` mirrors the backend vocabulary (`zcom-backend/packages/core/src/analytics/analytics-events.vocabulary.ts`: `StorefrontEventEnum`, `CtaEnum`, `CUSTOM_DIMENSION_PARAMETERS`, 100-char clip) by hand; keep both, and the deveshe twin `utils/analytics-events.util.js`, in sync. Send every non-e-commerce event through `trackEvent` or its typed helpers (`trackSelectItem`, `trackSelectVariant`, `trackCtaClick`, `trackGalleryInteraction`, `trackSizeGuideOpen`, `trackNotifyMe`, `trackCouponApply`/`trackCouponFailed`, `trackAddShippingInfo`, `trackAddPaymentInfo`, `trackCheckoutError`, `trackSearch`): it clips strings, drops empty values and hands the event to the kit's `trackEvent`. **`item_id` is always the identifier the e-commerce items use here, the variant `_id`** (first variant when none is chosen): take it from `getAnalyticsItemId(product, variant)`, never from a product id or slug, so the backend can join the event to the product. `reason` is the GraphQL `extensions.reason`/`code`, never message text; no PII in any parameter. **To add an event:** add the name (and its parameters) to the backend vocabulary first, mirror it in both storefront files, add a typed helper, and call it where the UI does the thing; list it in the PRD-013 pointer. The wired events and their components are in `docs/prd/PRD-013-behaviour-analytics-depth.md` §2; `search` is sent once per `/search` term with the result count (PRD-014 FR-2.8).
