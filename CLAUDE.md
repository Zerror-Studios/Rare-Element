## 0. Workspace rules (shared by every ZCommerce repo)

This repo is one part of the ZCommerce platform. The full map is in the workspace root `../CLAUDE.md` (`../../CLAUDE.md` for storefronts), when that file is present. The rules below are mandatory here even when it isn't.

1. **PRD first (tiered).**
   - **T1** covers: a new feature, page or module; a GraphQL contract change; a model or event change; auth, tenant, permission or billing logic; a new integration. T1 needs a PRD in `docs/prd/` with **Status: Approved** before any code. If none exists, draft one from `docs/prd/_TEMPLATE.md` (Status *Draft*) and **stop for approval**.
   - **T2** covers bug fixes, tweaks and small refactors. T2 needs only a line in `docs/changelog/YYYY-MM.md`.
   - Unsure of the tier? Treat it as T1 and ask.
   - Cross-repo PRDs have their source of truth in `zcom-backend/docs/prd/`; consumer repos keep a pointer PRD.
2. **Read docs before, update docs after (MANDATORY, no exceptions).** Documentation is part of the definition of done. Every change, including code, config, infra, dependencies and decisions, updates all related docs in the same change. Record decisions and approvals from conversation in the PRD or ADR immediately, before implementing. A task isn't finished while any doc disagrees with the code.
   - **Before** a change, read this file, `README.md`, `docs/README.md`, and the relevant PRD, ADR and architecture docs.
   - **After** it, in the same change, update whatever is now stale: the README (setup, commands, env names), `docs/architecture/*` (contracts), PRD status and implementation log, the changelog, `docs/README.md` (the index), and this `CLAUDE.md` (rules and known issues).
   - End every task with a **"Docs impact"** line.
3. **Ask, don't guess.**
   - Ask one precise question, with options and a recommendation, when the request conflicts with a PRD, an ADR, this file, or the code.
   - Do the same when docs and code disagree, or when a change would affect a contract, a security or tenant boundary, the design system, dependencies or deployment.
   - Don't ask about things you can verify in the code yourself.
4. **Scoped and safe.**
   - No drive-by refactors or mass reformatting.
   - Don't add dependencies without asking.
   - Never commit, push, deploy or touch databases unless asked.
   - Never print or commit secrets or `.env` values, including the token embedded in `git remote -v`.
   - Report checks honestly, keeping pre-existing failures separate from new ones.
5. **Coding style: the owner's signature (mandatory).** Follow the workspace `CODING_STYLE.md` (`../CODING_STYLE.md`, or `../../CODING_STYLE.md` for storefronts). Its baseline is the `zcom-backend` style.
   - 2 spaces, double quotes, semicolons, trailing commas, 80 columns.
   - Named exports with barrel `index.ts` files (React page and component files are the exception: `export default X;` at the end).
   - File names are `kebab-case.role.ts`.
   - Static-class controllers and services, with `return await`.
   - `xEnum = {…} as const`; the `I` prefix only for Mongoose documents; `UPPER_SNAKE` constants with unit suffixes (`_MS`, `_DAYS`).
   - `GraphQLError` with `extensions.code`; one `createLogger({ service })` per module.
   - JSDoc module headers and `// ─── ` section dividers.

   **New files** follow it exactly. **Edits** keep the file's existing formatting; never reformat untouched code. When you commit, use Conventional Commits: `type(scope): summary (PRD-NNN)`.
6. **Storefront specifics.**
   - Use only backend operations listed in the storefront contract doc, and validate field-level.
   - The server computes money.
   - **Plumbing lives in `@zcom/storefront-kit`** (PRD-002, the kit's `docs/prd/PRD-002-storefronts-onto-the-kit.md`): the proxy, the Apollo Client 4 link chain, the customer session, guest cart id, consent and tags, attribution, payment launcher and return, `/checkout/start`, stock and sort helpers, security headers. Fix a plumbing bug in the kit (every store gets it), never by copying kit code here. What stays here is Nahara's design, copy and the few store-specific flows listed in §2.

## 1. What this is

The **Rare Element** brand storefront (the brand name in content and assets is **Nahara**, `assets.nahara.co.in`, site `nahara.co.in`). It's a custom-designed shopper site on ZCommerce, with home, product listing and detail, category catch-all, account (orders, settings, wishlist; the fake offers page was removed by PRD-014 UX-06), checkout (the store's payment app: Nimbbl, Razorpay, Cashfree or PayU, PRD-011) and login. It is the **reference pattern for new storefronts**.

**Stack (PRD-002 D3, one version table with the kit and Deveshe Dreams, 2026-11-10):**
- Next.js 16.4 with the **App Router** (`src/proxy.js`, Turbopack), React 19.3, **JavaScript**.
- **`@zcom/storefront-kit` 1.x** (installed from its GitHub tag; builds need the shared `GITHUB_TOKEN`, `vercel.json`; its build-on-install is approved in `package.json` `allowScripts`, pinned to the tag's commit, so a new tag needs `npm approve-scripts @zcom/storefront-kit`), Apollo Client 4.3 (a kit peer: the store's own queries share the kit's client) + `@apollo/client-integration-nextjs` (the kit's `ZcomSsrProvider`), graphql 17, rxjs 7, zustand 5, react-hook-form + zod 4.

## 3. Rules

- **App Router conventions.**
  - A server `page.jsx` fetches data with the RSC client and exports `metadata` or `generateMetadata` (with a per-route canonical). Interactivity goes into a sibling `*-client.jsx` with `'use client'`. Add a `loading.jsx` for new routes, but **never a root `app/loading.jsx`**: a loading boundary above a page makes it stream, so its `notFound()` answers 200 and `permanentRedirect` can't be a 308 (the home skeleton lives in the `(home)` group for that reason; 2026-11-11). Product pages have none above them: they check the product, then show their own Suspense skeleton.
  - A client listing that keeps its products in a store renders the server's `initialProducts` until the store holds them (after mount), so the server HTML links every listed product (`products-client.jsx`, `category-client.jsx`; the kit's live check tests it).
  - Never import `next/router` (use `next/navigation`). Don't use Pages Router APIs.
  - Call `notFound()` only for a null result or `NOT_FOUND`; other errors go to `app/error.jsx`.
- **Caching.** Catalog pages use `export const revalidate = 300`. Keep account, cart and checkout dynamic, and never cache per-user data.
- **Data.**
  - Server components use `serverQuery` from `lib/server-query.js` (the kit's `zcomFetch`: it throws on any error except `NOT_FOUND`, so `notFound()` stays for real misses); client components use Apollo hooks (`@apollo/client/react`) under the kit's provider. `context.skipAuth` sends a request anonymously.
  - **`EDGE_SHARED_SECRET` is server-only.** Only the kit reads it (proxy, `zcomFetch`, the SSR pass of `ZcomSsrProvider`). Never prefix it with `NEXT_PUBLIC_`, and check `.next/static` for it after build changes.
  - Cart operations go through `useVisitor().runWithGuestId` (never invent a guest id client-side).
  - gql documents go in `graphql/`. No inline `gql`.
  - Show errors with `utils/errors.js` (branches on `extensions.reason` / `code`); every `PROMOTION_*` reason has its own message through `getPromotionMessage`, the store's copy else the kit's, never a generic fallback).
  - Site URL and support email come from `utils/env.js` (env with the current Nahara defaults). **Tag ids come from the backend (PRD-034 FR-1.2):** the kit's `ZcomTags` (`providers.jsx`) reads `storefrontTrackingConfig` and takes the backend GA4 / Pixel / Google Ads ids, else the env fallback it is given (`NEXT_PUBLIC_GA_MEASUREMENT_ID`, `NEXT_PUBLIC_FB_PIXEL_ID`; GTM is env only); malformed ids load nothing.
- **Auth and tokens.**
  - The session is the kit's (`tokenManager`): the access token lives **in memory only** and refreshes 60 s before expiry with `customerRefreshToken` (single-flight); the refresh token is the HttpOnly `__Host-zc_cust_rt` cookie; never select or store `refreshToken`. An auth answer (UNAUTHENTICATED, FORBIDDEN, INVALID_AUTH_TOKEN, TENANT_MISMATCH) ends the session and Nahara toasts "Your session has ended"; network, 429 and 5xx errors never do. `TENANT_NOT_FOUND` shows one "store unavailable" toast (`onStoreUnavailable`).
  - The legacy `refresh_token` cookie isn't forwarded by the kit's proxy (kit PRD-002 D10). A shopper's pre-kit sign-in hint, guest bag id, consent and click ids are moved to the kit's keys once on the first visit (`migrateLegacyStorage`).
  - Code sign-in (the sign-up too, PRD-041 FR-12) and password login honour `?next=` only through `utils/redirect.js` (same-origin check with `new URL`, RSEC-6); without a valid `next` they go to `/`. The Apollo store is reset at login and cleared at logout.
  - The persisted auth store holds no PII (RSEC-11: `partialize` + v1 migration); the profile is reloaded from `getMyProfile` after a reload.
- **Money and checkout.** The server computes every price and total. Checkout (`/checkout`, `app/checkout/checkout-client.jsx`): **both paths run on the kit's `useCheckout()`** (kit 1.1.0; signed in since 2026-11-12, PRD-041 pointer log). **One flow on both paths (owner, 2026-11-12, as Deveshe Dreams):** "Continue to payment" (the summary's submit button) validates the form and calls `start` (signed in) or `startGuest` (guest), waits for RESERVED and shows the server total; "Pay now" (`pay()`) is enabled only while the session is reserved for exactly the bag, coupon and details on screen, the news box included (`getDetailsKey` / `isReservedFor` in `utils/checkout-kit.js`), otherwise disabled with "Continue to payment to see your final total" (`OrderSummary` `showContinue` / `canPay` / `payLabel` / `onPay`). Signed in (`CustomerCheckout`): "Continue to payment" calls `start({ cartId, lines, email, shippingAddress, billingAddress })` (`utils/checkout-kit.js` `toCustomerCheckoutInput`: the form's addresses as `OrderAddressInput`, a saved address sent as its values, no coupon code: the bag's own applies on the server). The kit opens `createCheckoutSessionFromCart` with `buildAttribution()` and `buildCheckoutConsent()`, waits for RESERVED, completes it (a ₹0 total is placed PAID, COM-08, and goes straight to the paid answer), opens the store's payment app (`launchPayment`: Razorpay / Cashfree windows, PayU and CCAvenue form posts, Nimbbl until its 2026-11-15 shutdown through the store's `nimbbl_sonic`, `registerNimbblCheckout` in `app/providers.jsx`), verifies and waits for PAID. The summary shows the server total once reserved (else the bag's estimate, "Calculated at payment" shipping). Once paid: `orderStatusPath(statusToken)` when the kit has the token, else `/checkout/thank-you?orderId=…` (polls `myOrder` 3 s up to 60 s, ends on "Payment not confirmed yet", RBUG-20). A closed payment window: toast, "Pay again" (`retryPayment` of the same order; the kit sends GA4's `checkout_error` `PAYMENT_DISMISSED` with `provider`, the store doesn't). The ads begin checkout is sent once per page load on both paths (`hooks/useAdsBeginCheckout.jsx` → `trackEcomEvent.adsBeginCheckout`). A failed payment of the kit's kept order: `/checkout/payment-failed?orderId=…`, whose "Retry payment" pays any kept order (signed in or guest) with `retryPayment`; stock, price, coupon, `VARIANT_REQUIRED` and no-retry answers stay on the page with a toast (the bag re-read), `SHIPPING_UNAVAILABLE` / `ADDRESS_REQUIRED` focus the state field. **The unpaid order is the kit's** (`PendingOrderStore`, this tab, 2 h): "Continue to payment" (`start`) with the same bag and details (email, shipping, billing) reuses it and "Pay now" pays it again (also after a reload), changed details place a new order (VBUG-4; the backend cancels the old one, PRD-015 FR-14). The kit's fingerprint ignores the bag's coupon (no `promotionCode` is sent), so the store clears `PendingOrderStore` on any bag or coupon change and drops a kept order of another bag or coupon on load (`isKeptOrderStale`); the bag is locked only while the checkout is busy.
