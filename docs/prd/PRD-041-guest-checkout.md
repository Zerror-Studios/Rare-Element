This storefront's part is **FR-17**: checkout without signing in, sign-in with an email code (also the sign-up), and the order status page. Every new flow goes through the kit, so the store stays in step with it and with Deveshe Dreams (built the same day; its pointer PRD is the twin of this one).

## UX as built

- **Checkout (`/checkout`, `app/checkout/checkout-client.jsx`; was `/checkout/[id]` until later on 2026-11-12, see the log).** The default export picks the path from the kit's session and `useStoreCheckoutOptions()` (the page loader shows while either is read):
  - **One flow on both paths (owner, later on 2026-11-12, see the log; as Deveshe Dreams):** "Continue to payment" validates the form, opens the session (`start` signed in, `startGuest` for a guest), waits for RESERVED and shows the server total in the summary; "Pay now" is enabled only while that session is reserved for exactly the bag, coupon and details on screen (`isReservedFor` in `utils/checkout-kit.js`), otherwise disabled with "Continue to payment to see your final total", and calls `pay()`. Any change to the bag, coupon, contact or email, addresses or the news box disables "Pay now" until "Continue to payment" is pressed again. A closed payment window → a toast and "Pay again" (`retryPayment`).
  - **Signed in:** `CustomerCheckout`, on the kit's `useCheckout().start` / `pay` / `retryPayment` since later on 2026-11-12 (see the log): saved addresses and the address form, the kit's kept unpaid order reused while the bag and details match ("Continue to payment" finds it). Its client-side redirect to `/login` is gone (the path choice replaces it).
  - **Signed out, accounts OPTIONAL:** `components/checkout/GuestCheckout.jsx`, in Nahara's checkout layout (the same columns, inputs, address form and order summary):
    - **Contact** (`components/checkout/GuestContactDetail.jsx`): email and phone (required; the phone with its country code, 7–15 digits like the backend), first and last name, "Email me with news and offers" (unticked; sent as the kit's `contact.acceptsMarketing`, the guest's email consent, never `subscribeNewsletter`), and "Already have an account? **Sign in**" → `/login?next=/checkout` (the code sign-in merges the guest bag; back on `/checkout` the signed-in checkout opens the customer's own, merged bag). Names and phone fill the empty delivery fields on blur.
    - **Delivery:** the existing address form (`Delivery`; a guest has no saved addresses) and billing address, mapped to `OrderAddressInput` by `utils/guest-checkout.js`.
    - **Payment** (`OrderSummary`): "Continue to payment" calls the kit's `useCheckout().startGuest({ cartId, lines, contact, shippingAddress, billingAddress })` (the guest bag from `getCart(guestId)`, the kit's `guestCartStore` id) and shows the server total (shipping, tax, total); then "Pay now" calls `pay()` ("Pay again" after a closed window). The session (and its stock hold) opens only on that click (PRD-014 W0V2-02). Any change to the contact, the addresses or the bag after "Continue" needs "Continue" again; a coupon change also drops a kept unpaid order (the kit's fingerprint has the lines, not the coupon). The summary's bag and coupon edits send the guest id (`OrderSummary` `guestId`).
    - Refusals show the kit's message, or Nahara's own where it has one (`utils/errors.js` `getKitKeyMessage`), as a toast and inline at the end of the form: `INVALID_EMAIL`, `INVALID_PHONE` (scroll to Contact), `SHIPPING_UNAVAILABLE`, `ADDRESS_REQUIRED` (focus the state field), `SIGN_IN_REQUIRED`, `INVALID_GUEST_TOKEN` ("Your checkout timed out; your bag is saved", and the checkout starts over), stock and price answers (the bag is re-read).
    - Loading (the button spinner, the page loader while placing, verifying or leaving), field errors per field, a message for an invalid form, an empty or unloadable bag.
  - **Signed out, accounts REQUIRED:** "Sign in to check out" with a Sign in button (back to this checkout, the bag merged).
- **The bag drawer's Checkout** goes straight to `/checkout/<bag id>` for guests unless accounts are REQUIRED (then `/login?next=…`, as before). **`/checkout/start`** (checkout links) opens the guest's own bag the same way (once per visit).
- **After payment.** A paid (or still confirming) guest goes to `orderStatusPath(statusToken)`; with no token, the thank-you page. A failed payment of a placed guest order goes to `/checkout/payment-failed`, whose "Retry payment" pays the kept order with the kit's `retryPayment` (the guest checkout token is the kit's, this tab only; "View order" is hidden for a guest). The payment-return page (`usePaymentReturn`) goes to the status page whenever the kit has a status token (a signed-in shopper's once PAID; a guest's also while confirming), else thank-you as before. A paid signed-in order goes to the status page too when the kit has its token, else to the thank-you page. A failed payment of a placed signed-in order also goes to `/checkout/payment-failed`, which retries any kept order (signed in or guest) with `retryPayment`. The kit sends the browser ads purchase for every paid order in the paying tab (deduplicated per order, so the thank-you page's `PurchaseTracker` can't send it twice).
- **Sign in (`/login`, `components/login/CodeSignIn.jsx`).** The kit's `useCodeSignIn`: email → Continue → "Enter the code we sent to a•••@gmail.com" (one input, `autocomplete="one-time-code"`, numeric, paste and autofill; six digits submit on their own) → signed in. "Resend code" after the kit's countdown (60 s, or the server's `retryAfterMs`), "Use a different email", messages for `INVALID_LOGIN_CODE` and `RATE_LIMITED`. "Sign in with password instead" slides to the existing password form (FR-11, `Login.jsx`), which keeps "Forgot password?" and links back to the code. The panel out of view is `inert`. After sign-in `AuthContext.completeCodeSignIn` brings the store's state in step exactly as the password `login` does (logged-in flag, profile, "Some items from your bag could not be added" when the merge failed), then `?next=` through `utils/redirect.js`.
- **Sign-up (FR-12).** The sign-up form (`components/login/Signup.jsx`) and its `SIGN_UP_USER` (`CustomerSignup`) document are gone; the code sign-in creates the account. Name and phone are filled in Account › Settings when empty (the existing profile form). The mobile menu says "Sign in".
- **Order status page (`/orders/status/[token]`).** A server page on the kit's `getOrderStatus(token)` (never cached, the shopper's IP sent), body `components/orderStatus/OrderStatusView.jsx`: "Thank you, Priya! Order #NH1042 is confirmed" once paid (else "is waiting for payment" / "was cancelled"), the number and date, the timeline Confirmed → Shipped (courier, AWB, an https tracking link) → Delivered (date), or Confirmed → Cancelled, the items with images, subtotal / discount / shipping / tax / total, the delivery address as the server masks it, the payment status and the store's contact. A shopper who isn't signed in sees "Sign in with your email to see all your orders in one place" (to `/login?next=/account`); a signed-in one, a link to their orders (`OrderStatusSignIn.jsx`). An unknown or replaced token is a 404 with "Contact us" (`not-found.jsx`); a rate limit or outage shows an error with the contact, never a 404. Metadata `robots: noindex, nofollow`, `referrer: no-referrer`, canonical `/orders/status` (never the token); the kit's proxy also sends `X-Robots-Tag`, `no-store` and `Referrer-Policy: no-referrer`.
- **Account.** The order detail (`/account/order/[id]`) shows "View order status" (`useMyOrderStatusToken(orderId)` + `orderStatusPath`).
- **Proxy.** `/checkout` left `loginGuard.paths` (only `/account` is guarded; the old checkout `publicPaths` went with it); `/orders/status/` needs no guard.

## Decisions taken here

- The signed-in checkout first kept its own code; the owner then asked for it on the kit too (same day, as in Deveshe Dreams), so both paths run on `useCheckout()`. It first kept Nahara's single "Pay Now" step; later the same day the owner chose one flow for both stores and both paths ("Continue to payment" → "Pay now", see the log).
- "Already have an account? Sign in" returns to `/checkout` (the checkout loads the customer's own cart), not to `/checkout/start?resume=1` as in Deveshe Dreams, whose checkout start has a resume step this store doesn't.
- The test harness (`test/register-hooks.mjs`) now resolves `.jsx` files too, as Deveshe Dreams' does, so the zod `GuestCheckoutSchema` is tested in Node (only JSX-free `.jsx` files can be loaded).

## Not done / known gaps

- **Browser purchase events on the status page.** The status page itself fires none (it is a public page the emails also open). The tab that paid sends the ads purchase (kit, guests and signed-in shoppers).
- `/checkout/thank-you` reads `myOrder`, so a guest who lands there (no status token) sees "We couldn't find this order"; the kit returns a status token for every placed guest order, so this needs a failed token read.
- Not browser-tested; no run against a live gateway, the kit's live check or a payment sandbox.
